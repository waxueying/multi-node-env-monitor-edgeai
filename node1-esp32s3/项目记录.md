# structure_monitor 模块笔记

> ESP32-S3 仓储货架监测项目 · 结构安全检测核心算法
> 位置：components/bsp/structure_monitor.c / include/structure_monitor.h

---

## 一、模块定位

输入加速度，输出「结构安全事件」的纯规则算法模块。

不依赖硬件、不依赖 FreeRTOS、不依赖 AI，只有数学运算。调用者每 10ms 喂一帧加速度（100Hz），它返回这一帧是否产生了事件。

三个检测维度：

| 维度 | 物理含义 | 对应现实事件 |
|---|---|---|
| 撞击 | 瞬时动态加速度超阈值 | 叉车撞货架立柱 |
| 倾斜 | 姿态相对安装基准的偏移 | 立柱被撞变形 |
| 振动 | 动态分量 1 秒 RMS | 结构松动、持续异常振动 |

---

## 二、三个核心概念（理解一切的基础）

### 1. 动态分量 dyn

定义：当前加速度 - 重力估计，取模长。

为什么需要它：传感器静止平放时读数不是 0，而是 z 约等于 1.0g（重力本身）。直接拿原始加速度判撞击，静止时就有 1g 的基线，没法设阈值。减去重力后静止时 dyn 约等于 0，任何运动都会让 dyn 升高——这才是「运动量」。

```c
dx = ax - s_grav[0];  dy = ay - s_grav[1];  dz = az - s_grav[2];
dyn = sqrtf(dx*dx + dy*dy + dz*dz);
```

撞击、振动都基于 dyn 判断。

### 2. 重力估计 s_grav

定义：对重力方向的低通滤波跟踪值。

关键设计：只在「准静态」（dyn < 0.15g）时才更新。撞击和振动期间冻结，避免把冲击加速度误当成重力方向吸收进去。

```c
if (dyn < SM_GRAV_UPDATE_LIMIT_G) {
    s_grav[i] += SM_GRAV_LPF_ALPHA * (a[i] - s_grav[i]);   // alpha = 0.01
}
```

它跟踪的是「缓慢变化的真实重力方向」，能容忍温度漂移和慢速倾斜，但不受瞬时冲击影响。

### 3. 安装基准 s_baseline

定义：上电头 1 秒（100 个样本）的平均重力方向，作为「货架正常姿态」的参考系。

为什么：倾斜检测的真正需求不是「绝对倾角」，而是「相对安装时的姿态偏移了多少」。货架装在倾斜的地面上？没关系，基准就是那个倾斜姿态，相对偏移仍为 0。只有当立柱被撞歪、姿态相对安装态发生固定偏移时才报警——这正是「结构变形」的特征。

## 三、三个检测功能的原理

### 1. 撞击检测（状态机）

不是单点判断，是三阶段状态机：

```
空闲 ──[dyn > 0.5g]──> 撞击中 ──[dyn < 0.2g 连续 5 次]──> 结束，报事件
                          |
                          +──[超过 200 样本 / 2s]──> 强制结束
```

- 触发：dyn > 0.5g，进入撞击态，峰值 = 当前 dyn
- 持续：每次采样取 max，实现「峰值保持」
- 结束：dyn < 0.2g 连续 5 次，或超时 2 秒兜底
- 上报：结束时产生一次事件，携带整个过程的最大值

为什么用状态机而不是单点判断：一次撞击持续几十到几百毫秒（跨越多个采样点），如果每个超阈值的采样点都报一次事件，一次碰撞会产生一串重复报警。状态机把它归并成「一次事件 + 一个峰值」。

为什么结束阈值（0.2g）低于触发阈值（0.5g）：滞回。撞击波形是衰减振荡，如果用同一阈值判断结束，会在阈值附近反复进出撞击态，一次碰撞被算成多次。

为什么要有 2 秒超时：防止异常情况（传感器故障持续输出高值）导致撞击态永久卡死，再也不会产生新事件。

### 2. 倾斜检测（带滞回）

```c
tilt_deg = angle_between(s_grav, s_baseline);   // 两个 3D 向量夹角

if (!alarm && tilt_deg > 2.0)  -> 报警，报事件
if ( alarm && tilt_deg < 1.0)  -> 解除，报事件
```

夹角用点积公式算：cos(theta) = (v1 点乘 v2) / (|v1| * |v2|)，再 acos 转角度。做了 clamp 防止浮点误差导致 cos 略微越界（acos 定义域是 [-1,1]，越界返回 NaN）。

滞回的意义：报警 2 度 / 解除 1 度之间是死区。倾角在 2 度附近抖动时状态不变，避免事件风暴。

### 3. 振动监测（滑动窗口 RMS）

```c
s_vib_win[s_vib_idx] = dyn;                 // 写入环形缓冲
s_vib_idx = (s_vib_idx + 1) % 100;          // 指针循环
s_vib_count++;                              // 有效样本数（上限 100）

RMS = sqrt( sum(dyn^2) / count );           // 均方根
```

为什么用 RMS 而不是平均值：振动信号正负交替，直接平均会相互抵消趋近 0。RMS 先平方（消除符号）再平均再开方，反映「能量水平」，这是振动测量的标准做法。

窗口取 1 秒（100 个样本 @100Hz）：既平滑掉偶然抖动，又及时反映状态变化。窗口太短噪声大，太长响应慢。

环形缓冲：定长数组 + 循环索引，写满后新数据覆盖最旧的。不需要搬移数据，O(1) 写入。

## 四、完整数据流

```
structure_monitor_update(ax, ay, az)
    |
    +- [未标定] 累加 100 个样本 -> 算出 baseline -> return 0
    |
    +- [已标定]
         +- 算 dyn = |a - grav|
         +- 准静态？-> 更新 grav（低通）
         +- 算倾角 -> 判断报警/解除 -> 事件位
         +- 更新振动窗口 -> 算 RMS -> 状态
         +- 撞击状态机 -> 可能产生事件
    |
    +- return events（位掩码）
```

返回值与状态的分工（重要）：
- update() 返回的是本次新产生的事件（只在状态跳变那一刻出现）
- get_status() 返回的是当前状态快照（每帧都是最新的）

main.c 里两种都用：事件用来打日志/发 CAN 事件帧（不重复刷屏），状态用来填周期上报帧（每秒都在报当前值）。

## 五、设计决策与理由（面试必答）

### Q: 为什么用「加速度 - 重力估计」而不是直接看加速度？
静止时加速度读数约 1g（重力），有固定基线，没法直接设阈值。减去重力后静止时约 0，运动量一目了然。

### Q: 重力估计为什么只在准静态更新？
撞击瞬间 dyn 很大，如果此时仍更新 grav，会把冲击加速度当成重力方向吸收，导致撞击后倾角计算错乱。加门限（dyn < 0.15g）后，冲击期间 grav 冻结，倾角计算不受污染。

### Q: 倾斜为什么要标定基准，不用绝对角度？
实际需求是检测「相对安装态的变形」，不是测绝对倾角。货架装在倾斜地面或墙面本身不垂直都正常，标定后这些都被归零，只有相对变化才报警。

### Q: 为什么阈值都带滞回？
真实信号在阈值附近会抖动，没有滞回会在阈值上下反复穿越，一次事件变成几十次报警，串口刷屏且污染 CAN 总线。

### Q: 撞击检测为什么不用简单阈值？
一次撞击跨越多个采样点，简单阈值会给每个点报警。状态机 + 峰值保持把它归并成一次事件并保存最大强度，信息量更大。

### Q: 三个检测为什么放在一个函数里？
它们共享同一个中间量 dyn 和 grav 估计，拆开要重复计算或传参。放一起更紧凑，且都在同一采样节拍下，时序天然对齐。

## 八、几个容易踩的坑

### 1. 加速度单位是 g，不要除以 16384
esp-idf-lib 的 mpu6050_get_acceleration() 内部已做换算（raw * 2.0/32768，随量程自动调整），返回值就是 g。早期代码按「原始 LSB」除以 16384，导致输入被抹成近似 0——这是之前 AI 版本输出恒为 0 的根因之一。

### 2. 量程要选 +-8g
默认 +-2g，撞击峰值很容易削顶（超过量程的读数被截断成满量程），峰值测量失真。改成 +-8g 后余量充足。

### 3. 模块无锁，但要求同核调用
内部状态是普通 static 变量，没加互斥。当前 main.c 里只被核心 1 的采样任务调用，安全。如果以后要在别的任务/核心调 update()，需要加临界区。

### 4. 调用周期必须稳定
dyn 是差分计算，阈值（0.5g）和时间强相关。main.c 用 vTaskDelayUntil（绝对时间唤醒）而不是 vTaskDelay（相对延时），就是为避免累积漂移改变实际采样率。

### 5. 函数无阻塞、无 I/O
内部只有 memset、sqrtf、acosf，纯计算。放 100Hz 任务里没有负担（实测远小于 10ms 周期）。

先说最容易被忽略的一点：ESP8266 只负责 TCP，MQTT 协议栈是跑在 STM32 的 paho 里的。模块本身不懂 MQTT。ESP32 才有内置的 MQTT AT 命令。这个区别面试常被追问。
阶段一：让模块自己能上网
1. 选错了 WLAN —— ESP8266 不支持 WPA3
你机器上有两个配置："Penguin King" 是 WPA3-Personal(GCMP-256)，"your-wifi-ssid" 是 WPA2-Personal。ESP8266 的 AT 固件最高只到 WPA2，WPA3 的 SAE 握手它做不了，所以必须连 WPA2 那个。
知识点：ESP8266 芯片本身不支持 WPA3；想用 WPA3 得换 ESP32 或更新版 SDK。看你 PC 的配置可以用 netsh wlan show profile name="xxx" key=clear 直接看到加密类型。
2. 串口引脚
先是 TX=A1 / RX=A0，跑不通，最后定在 PA2/PA3（USART2）。UART 必须交叉：MCU 的 TX 接模块的 RX。
3. 验证顺序（这是个方法论，值得讲）
你插 USB 到 ESP-Link 底板能被认成 COM13，这时是模块直连 PC。正确的验证阶梯是：
模块单独 → MCU 能跟模块对话 → 模块能上网 → MCU 的协议栈能上网 → 上层应用
每一级都单独验，出问题就知道卡在哪一级。不要一上来就把 STM32 和 paho 全接上。
4. AT+CWJAP 一直 WIFI DISCONNECT / WIFI CONNECTED 抖动
过程回显不可信。可靠的判定是查状态：
AT+CWJAP?
+CWJAP:"your-wifi-ssid","54:a7:03:71:fd:88",1,-50,0
OK
信道 1，RSSI -50dBm（信号挺强）。再用 AT+CIFSR 拿到 STAIP,"192.168.0.103"，说明真连上了。
知识点：查状态用 ? 形式，别读过程回显。
阶段二：让 RT-Thread 认到这张网卡
5. ping 返回 32 bytes from 0.0.0.0，time=134357406ms
这个荒谬的 time 和 0.0.0.0 说明网络层没真正就绪。用 ifconfig 看 FLAGS：
FLAGS 状态	含义
UP LINK_DOWN INTERNET_DOWN	网卡在，但没跟 AP 建链
UP LINK_UP INTERNET_UP	才算真通


这里的关键是 LINK_UP 不等于能通信，还要 INTERNET_UP（对端可达）。
6. dns esp0 223.5.5.5 失败 —— 这条最值得讲
报错：
[E/at.clnt] execute command (AT+CIPDNS=1,"223.5.5.5") failed!
[E/at.dev.esp] esp0 device set DNS failed.
根因：RT-Thread 的 at_device 驱动用的是新版 AT 命令形式 AT+CIPDNS=1,"x"，而你这颗模块的固件是 1.7.4.0，只支持查询形式 AT+CIPDNS_CUR?，不支持设置。所以命令发过去直接失败。
这就是那个坑：裸 AT 能通 ≠ 驱动能通。at_device 是按某个 AT 固件版本写的，固件和驱动的命令集必须匹配。排查方法是直接去读驱动源码里用的 AT 命令，跟模块手册对照。
后来域名解析是靠模块自己做的（AT+CIPDOMAIN="www.baidu.com" → +CIPDOMAIN:157.148.69.151），AT+PING="223.5.5.5" → +38（38ms）。再之后 RT-Thread 里 ping www.baidu.com 也通了，25ms。
知识点：域名解析有两条路 —— lwIP 侧自己查，或者把域名丢给模块用 AT+CIPDOMAIN 查。固件不支持前者时就得走后者。
7. AT+CWLAP 卡死
扫描 AP 是长阻塞操作，在交互式 AT client 里会把回显通道占死。这类命令要用独立线程 + 超时，不能在交互模式里发。
8. 状态残留
重新插拔过一次、电脑关机过一次之后，模块状态机卡住了，得重进 at client uart2（而且第一次还报 ERROR，第二次才正常）。重连之前先复位要成为习惯。
阶段三：打通 MQTT
9. Mosquitto 2.x 默认拒绝外部连接
这是最常见的"连不上 broker"陷阱。Mosquitto 2.0 起改了安全默认：不显式配置的话只监听本机回环。必须写 listener 1883 + allow_anonymous true。你那份 mqtt.conf 就是为这个存在的。
10. 先写 tcp_test 再上 paho —— 这是最值钱的调试方法
你没有一上来就调 paho，而是先在 STM32 上手写了一个最小 MQTT 握手：
[tcp_test] 目标 broker = 192.168.0.102:1883
[tcp_test] 1/4 socket 创建成功，fd=3
[tcp_test] 2/4 TCP 连接成功
[tcp_test] 3/4 CONNACK 成功，MQTT 握手通过
[tcp_test] 4/4 已发布到主题 maintest/probe
broker 侧同时看到：
New connection from 192.168.0.103:43090 ... as stm32_probe
Sending CONNACK to stm32_probe (0, 0)
Received PUBLISH from stm32_probe (d0, q0, r0, m0, 'maintest/probe', ... (25 bytes))
面试这么讲：分层定位。socket → CONNECT/CONNACK → PUBLISH，每一层单独证通。如果 paho 挂了，你能立刻排除"网络不通"和"broker 配错"，直接定位到库本身。反过来如果没有这一步，paho 一挂你就得同时怀疑网络、broker、库、配置四个东西。
顺带把 MQTT 最小握手背一下：
报文	作用
CONNECT	客户端 ID / keepalive / will / clean session
CONNACK	返回码，(0,0) = 接受
PUBLISH	topic + payload + QoS + retain


broker 日志里那串 (d0, q0, r0, m0) 分别是 dup / QoS / retain / message-id。
阶段四：CAN → MQTT 全链路
11. 静默丢帧 —— rt_mq_recv 返回值语义变更（最值得讲）
现象非常反直觉：CAN 接收完全正常（串口一直刷 [D/can_receiver] CAN ID: 0x456），但 MQTT 一帧都没发出去。三个关键观测：
观测	排除了什么
OLED CAN RX Queue: 0	队列不是堆积，消费者在干活
没有 CAN message queue full 警告	生产端没堵
一条 Published to ... 都没有	问题在消费者到 MQTT 之间


「队不堆积、生产端不堵、消费端没输出」——这三条合起来只有一种解释：帧被取走了，但结果被判成失败丢掉了。
根因：工程内核是 RT-Thread 5.1.0。从 5.1 起 rt_mq_recv() 成功时返回的是收到的字节数，不再是 RT_EOK。原代码：
err = rt_mq_recv(can_rx_queue, data, sizeof(can_data_t), timeout);
if (err != RT_EOK) return -1;
can_data_t 是 20 字节，返回值 20 ≠ 0，所以每一帧都被判为失败。数据其实已经拷进结构体了，函数却返回 -1，上层 == 0 的判断永远不成立 → 静默丢弃。
修法：
received = rt_mq_recv(can_rx_queue, data, sizeof(can_data_t), timeout);
if (received != (rt_ssize_t)sizeof(can_data_t)) return -1;
注意只改 recv 侧，rt_mq_send() 成功仍然返回 RT_EOK，没变。
面试怎么讲：这是典型的 API 语义变更型 bug——编译器不报错、类型也对、逻辑全错。移植第三方 RTOS 代码时最该盯的一类问题。而且排查路径本身也值得讲：从「三个观测唯一推出一个结论」而不是瞎猜 CAN 或 WiFi。
12. CAN 进错误被动（REC 255）—— 波特率被覆盖
OLED 上出现过 REC 255 TEC0 LEC0。REC > 127 表示 CAN 控制器进了错误被动状态，典型原因是波特率不匹配 → 错误帧暴涨。
根因是初始化顺序：必须先 rt_device_open，再 rt_device_control(RT_DEVICE_CTRL_CONFIG)。如果反过来，open 时注册的默认 1Mbps 会把你的 500k 覆盖掉（BTH/BTR 寄存器低 10 位是「预分频 - 1」：500k 对应 6，1M 对应 3）。
13. 还没修的一个点（面试也可以主动提）
data_forward_thread_entry 在 MQTT 未连接时是静默丢帧的：只有走到 mqtt_client_publish() 才累加 dropped 计数，网络断了计数不涨，所以 OLED 诊断页看不出真实丢帧。改进方向是在未连接分支里也记账。

Q：为什么要 dns？模块不是能解析吗？
两条路：lwIP 侧自己查（需要向模块下发 DNS 配置，就是卡住的那条），或者把域名交给模块用 AT+CIPDOMAIN 查。固件不支持前者时只能走后者。
Q：ESP8266 和 ESP32 在你这套架构里的差别？
ESP8266 只做 TCP 透传，MQTT 由 MCU 的 paho 实现；ESP32 可以跑 ESP-AT，用 AT 命令直接发 MQTT。所以你换成 ESP32 的话，paho 那层可以省掉，但也就少了协议栈的可控性。
Q：怎么定位"数据没从 A 到 B"？
三端对照：生产者（队列长度、队列满告警）→ 消费者（有没有处理日志）→ 下游（broker 日志 / mosquitto_sub）。三端一对照，丢在哪一层是唯一的，不用猜。

list_device	确认设备注册（uart2 / can1 / i2c1）
